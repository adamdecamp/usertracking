# R.A.P.T.O.R. — Role-Based Access Personnel Tracking & Oversight Registry

<img src="public/raptor-icon.png" alt="R.A.P.T.O.R. raptor claw and verified document mark" width="96" height="96">

R.A.P.T.O.R. is a portable Windows administrative evidence tracker for information-system users, access documentation, training, and inspection readiness.

A lightweight Windows administrative tool for tracking information-system users, access roles, training requirements, and supporting evidence. The portable application runs locally, opens its interface in the default browser, stages day-to-day work in a protected per-user local workspace, and publishes verified records and ZIP evidence to a user-selected shared directory.

## Download

Use the executable attached to the latest GitHub Release. Every release also includes a one-page executive capability summary. Public releases are blocked unless the Windows executable has a valid Microsoft-backed Authenticode signature. Verify the signature from **Properties → Digital Signatures** and compare the executable and PDF SHA-256 values with `SHA256SUMS.txt` before use.

## Security model

- Binds only to the local loopback interface.
- Records the active Windows account in consequential audit entries.
- Does not transmit tracker data or evidence to an external service.
- Uses the modern Windows Explorer folder picker in the foreground; the local launcher owns atomic manifest, backup, evidence, audit, and lease writes instead of relying on browser lifecycle events.
- Protects the live database manifest with a SHA-256 sidecar written and recovered in the same transaction as the manifest. Full Access verifies that checksum, the newest valid backup, and the complete audit chain before editing is enabled. An interrupted or invalid newer backup is skipped and recorded while the newest valid backup is used; when the live manifest checksum and audit chain are healthy, a missing usable backup is rebuilt from that verified live state. A genuine manifest or audit-integrity failure preserves the records and falls back to Read-Only Access.
- Prompts at launch for **Read-Only Access** or **Full Access**. Multiple Read-Only sessions can search, filter, inspect user status, and view the audit log without taking the editor lock. Evidence-location controls are hidden, and the launcher rejects direct File Explorer location requests and shared-folder mutations from Read-Only sessions. Read-Only sessions time out after 15 minutes of inactivity, and their start, reconnect, system-switch, timeout, and logoff events are recorded with the active Windows identity.
- Authenticates every local launcher API request with a fresh 256-bit session token that is issued at process start, removed from the browser address immediately after launch, and never persisted beyond that browser session. The Windows launcher—not a browser-supplied mode—authorizes Read-Only and Full Access. All protected mutations are rejected unless the request also owns the active system lease.
- Exports one-organization, SHA-256 integrity-checked `.raptor-status.json` snapshots for ISSO distribution. Each snapshot includes active and disabled users but excludes evidence documents, shared paths, audit logs, and every other organization. Operators can optionally apply authenticated AES-256-GCM encryption with a 12-character-or-longer passphrase; the passphrase is never stored or included in the email and must be shared separately. The same portable executable opens plaintext or encrypted attachments offline in enforced Read-Only mode, and Full Access can create an Outlook draft with the ISSO in the To line and the snapshot attached.
- Supports mapped drive letters and UNC network-share folders, probes create/write/read/delete compatibility before saving a mapping, and applies bounded exponential retries to folder availability, metadata reads, evidence validation, hashing, manifest reads, directory enumeration, and verified writes for laggy on-site or VPN SMB connections. Safe read-only requests retry temporary busy, throttling, and gateway responses up to four times; the launcher queues reads for 30 seconds and file-changing requests for two minutes before reporting that storage is still busy. The launcher uses broadly compatible buffered file operations and SHA-256 verifies replacements. Sync avoids metadata calls for irrelevant file types, isolates unreadable evidence as reviewable file errors only after the network retry budget is exhausted, and retries directory enumeration with native and Explorer-compatible fallbacks when a provider rejects the normal pattern. Failed replacement attempts preserve or restore the previous verified file and return operation- and folder-specific diagnostics.
- Reduces SMB round trips with a unified Archive-preflight-and-discovery pipeline, one-pass directory enumeration and metadata reuse, resumable Sync journals, checksum-protected organization-sharded Sync indexes, organization-sharded authoritative database storage, advisory Windows change notifications, and a Windows-user-protected verified logical-database cache in local performance storage. Startup restores all cached status locally, contacts only the selected mapped system, and reuses the fully verified database returned by the integrity check instead of downloading its catalog and organization shards a second time. Read-Only opens the protected cache immediately and refreshes only the selected system in the background; Full Access remains locked until the selected database, newest backup, and audit chain pass verification. Rapid UI edits are coalesced for five seconds before a background shared-drive commit, while explicit record actions, Sync, logoff, and shutdown still save immediately. A small commit-last catalog references immutable, content-addressed, SHA-256-protected organization record shards and preserves the original record order; full verification checks the catalog and every shard. A watcher hint safely prioritizes a changed organization, but it never suppresses authoritative enumeration; missed, delayed, or overflowed network notifications therefore cannot hide evidence. Unchanged manifests are recognized from the small checksum and file metadata before the full database is read. Changed record state transfers only changed organization shards before committing the small authoritative catalog, while repeated compressed snapshot and daily CSV backup work is coalesced for up to 30 seconds and force-flushed at logoff or shutdown. New or changed evidence is transferred once to a short-lived per-user local validation cache, processed with storage-aware bounded concurrency, and then reused by the browser analysis instead of being downloaded from the share twice. A two-worker PDF pool avoids repeated worker startup while recycling workers by age and use count. The evidence cache is pruned before Sync and removed when the launcher exits. Per-phase timing, file counts, staged bytes, cache hits, concurrency, P50/P95 latency, watcher state, pending-backup state, index-shard count, database-shard count, storage format, backup compression, and audit-checkpoint status are available from the local-only **Performance** report and its JSON download; no user record or evidence content is included. Journal writes are batched and exact verified mutation paths are reused. Authoritative evidence, catalog, and organization shards remain on the mapped shared drive. Routine status, organization lists, and location lookups use the protected local JSON database and local workspace. Launch also checks immediate folders under the selected local workspace’s `Organizations` directory, recognizes manually created organizations, and prepares their direct organization-root intake, Rework, and Complete folders. Disabled-user history never triggers Archive discovery. Network-folder discovery requires explicit Full Rescan, including when using Legacy Import.
- Holds an exclusive Windows file lock only for Full Access while a system folder is active, preventing a second editor from acquiring write access on lock-capable SMB/Windows shares while allowing concurrent Read-Only viewers. Launcher storage queues are isolated per mapped system, so a slow operation against one system does not block independent work against another.
- Writes complete storage diagnostics to one daily text report under `System\Error Reports`, including startup-verification failures recorded after the app safely falls back to Read-Only Access. Every disconnected or blocked screen offers **End Session Safely**, which releases the editor lease when possible, preserves the protected local recovery workspace, and closes the launcher instead of trapping the operator in a reconnect loop.
- Keeps the Full Access working database in a per-Windows-user local workspace protected with Windows DPAPI, a restrictive user/System ACL, and a SHA-256 sidecar. Each local organization uses its organization root for intake and owns `ORG Rework` and `ORG Complete`; none of those workflow folders is created on the shared drive. Archive-bound evidence waits in `ORG Complete/Pending Upload`, while successfully published local copies move directly to `ORG Complete`. A source PDF is deleted only after the replacement ZIP is reopened, validated, and matched to the PDF by SHA-256. Document-type and Archive folders are created only in authoritative shared storage. A DPAPI-protected local evidence map keeps the shared destinations separate from physical local paths. Session publication is change-driven and commit-last: a true no-op returns without rewriting records or touching evidence; a JSON-only change publishes only the database, CSV, backup, and transaction metadata; evidence preparation runs only when pending evidence, an associated local workflow file, or interrupted recovery work exists. For an evidence change, ZIP evidence is streamed and verified first, a protected append-only progress journal records each completed transfer without rewriting the complete recovery plan, and the shared database catalog changes only after all evidence transfers pass. Ordinary commits use the evidence map rather than recursively enumerating the local workspace; a full recovery walk occurs only when a legacy workspace has no map. Operation-scoped hash caching avoids reopening the same evidence during preparation and verification. At the exact publication destination, differently packaged ZIPs containing the same validated PDF reuse the existing shared ZIP and its hash. A duplicate ZIP newly placed in the organization root is preferred over an older local publication receipt, matched by its embedded PDF hash, and drained after the authoritative shared copy is verified. Genuinely different archived PDFs retain both versions with a deterministic content-hash conflict filename; different active evidence still requires collision review. Database and CSV follow the resolved destination, while published-evidence receipts are stored in organization-specific shards so a commit rewrites only affected organizations. These checks never enumerate shared evidence folders. A failed publication leaves the protected local session intact for a safe retry. A successful Session Commit drains every published file from the organization root and Pending Upload into Complete; deferred or failed items remain visible for review instead of being reported as completed.
- Starts every release with no systems or users and does not retain operational records in browser storage.
- Creates a top-level `Organizations` folder in every mapped system. Operators add organization folders through **Manage Organizations**; an information system's descriptive Organization field never creates a local or shared organization folder. Local workflow folders are prepared only for operator-created folders or organizations represented by actual user records. Reserved document folders such as `SAAR` cannot be mistaken for organizations.
- Lets Full Access operators edit each system's name, type, and organization or delete its app registration. Deletion is recoverable: the mapped folder, evidence, manifest, audit history, and backups are retained and can be mapped again.
- Validates shared manifests, filenames, request paths, and CSV output.
- Migrates historical change-history entries that predate the non-identity `rolesBefore`, `rolesAfter`, and `files` arrays before applying strict manifest validation, preventing valid older databases from blocking Full Access or Sync while retaining all identity, evidence, checksum, and authorization checks.
- Accepts only readable PDF evidence or a ZIP containing exactly one readable PDF, with archive path, size, entry-count, encryption, and expansion-ratio safeguards.
- Never starts Sync automatically on launch, folder mapping, or information-system selection. Every organization in the protected local workspace accepts new evidence directly in its organization root and corrected evidence in its prefixed Rework folder such as `GDMS Rework`; the shared drive does not receive local workflow folders. The Sync chooser defaults to **Daily Sync — Fast and Strict**, which scans only the local organization root and Rework in the selected scope. **Full Rescan** intentionally inspects shared active document-type folders without applying loose-PDF compression, while **Legacy Import — Historical Recovery** performs broader onboarding and historical-repair discovery. A Sync can cover the mapped system or exactly one immediate folder beneath `Organizations`; document-type and deeper subfolders are not selectable scopes.
- Keeps the main **Sync** action available while earlier review or Clean Up results are pending. A later successful full or targeted Sync replaces those results with a fresh review; a stopped or failed scan preserves the earlier review.
- Uses a checksum-protected Sync index in each mapped system folder to skip reopening unchanged evidence. Daily Sync scans only each local organization root and Rework, reuses unchanged Rework validation, and opens only new or changed evidence. Legacy Import revalidates historical evidence in the local workspace. Only explicit Full Rescan scans network folders and performs shared Archive storage repair; Archive contents never reconstruct disabled-user status. The evidence-validation cache version is independent from ordinary application releases, and unchanged evidence avoids per-file recovery-journal writes. Shared Archive preflight handles administrative SAAR archival, storage repair, and invalid formats but never compresses or deletes a network PDF and never removes active evidence merely because it is overdue. Evidence-validation changes invalidate the index. Current-location refresh, stale-reference retry, and Reconciliation discovery read path, filename, size, and modified metadata only; only relevant targets are opened afterward.
- Opens a recorded artifact's verified current location in Windows File Explorer with the file selected instead of transferring or rendering the document inside the browser. New manual uploads retain a baseline SHA-256 so Reconciliation can detect content changes under an unchanged filename.
- Includes a read-only Reconciliation Center scoped to evidence already reflected in the User Directory database. It focuses on file collisions, changed content, duplicate identities or emails, conflicting Active/Disabled states, organization conflicts, and rejected recorded evidence while leaving Missing compliance requirements to normal reporting. Unrecorded files and every file in Archive or Rework are ignored. A completed run can generate a checksum-protected PDF correction report with every finding, affected path, and recommended action.
- Uses filenames as the primary identity and organization source, with a fillable-form fallback for standard DD Form 2875 XFA packets and the derived SAAR AcroForm. Scanned or flattened SAAR copies cannot create users automatically.
- Applies filename rules case-insensitively across identities, organization tags, artifact keywords, extensions, role markers, disabled markers, and month text while retaining the canonical output naming convention.
- Treats Privileged User Types as case-insensitive identifiers. Values such as `_DEV`, `_dev`, and `_Dev` are stored, filtered, grouped, and reported once as `_DEV`.
- Applies the role and Privileged User Type from a verified replacement SAAR to an existing user during Sync. For example, a `PRIV_DEV_SAAR` changes the matched General record to Privileged `_DEV` only after the exact SAAR passes provenance verification; the change is displayed for review and recorded in Administrative Change History and the tamper-evident audit log. `_DADM`, `_ADM`, `_PADM`, `_CYBER`, `_DTA`, `_DEV`, `_CDA`, `_CCL`, and other valid underscore types use the same case-insensitive path. Missing supporting evidence never blocks the verified elevation; each absent annual requirement remains Missing.
- Applies an explicit one-year expiration rule to DoD Cyber Certifications, 8140 Certification Memos, DTA Training, Privileged User Training, and User Agreements. SAARs remain non-expiring account-action records.
- In both modes, recognizes common valid filename date formats and atomically normalizes nonstandard dates to `DDMMMYYYY` before matching. Daily Sync performs safe filename-only corrections across in-scope evidence without reopening unchanged PDFs; Legacy Import adds the broader historical recovery pass.
- Runs the Document Renamer normalization engine automatically inside both Sync modes without exposing a separate main-page button. Daily Sync applies filename-only normalization to in-scope evidence and reads PDF content only for new, changed, or moved noncanonical files. Legacy Import also reads eligible unchanged historical candidates. The engine matches existing users and uses each PDF's immediate containing-folder name as the authoritative organization in the canonical filename. Root-level PDFs use the system organization. A complete valid filename date is reused without requiring a duplicate labeled PDF date. Legacy `Responsibilities` and non-DTA `Course` wording normalize to Privileged User Training; DTA `Course` or `Responsibilities` wording normalizes to DTA Training; and `Awareness` wording normalizes to DoD Cyber Cert. An unchanged SHA-256 is verified after every automatic rename. Ambiguous and image-only files remain available in Sync review or Rework and are never guessed.
- Automatically compresses every validated loose PDF that is being committed to a User Directory record inside the protected local workspace. Compression creates the ZIP locally, reopens it, validates its one-PDF structure, and verifies the embedded PDF hash before deleting the original PDF. A creation, validation, hash, or deletion failure leaves a recoverable transaction and never replaces the database with an unverified reference. Before session publication, any remaining associated local PDF is validated and compressed into a verified ZIP, and its database and CSV references are updated together. Unassociated loose PDFs remain local for review and do not block unrelated verified records. Only the verified ZIP is published to the shared drive. Shared-drive scans never compress, replace, or delete a loose PDF; an existing network PDF is preserved and reported for manual review.
- Enforces a fail-closed filename gate before document-type organization. Fault-tolerant input names are normalized first, but only a complete canonical `Last_First_(ORG)_Artifact_DDMMMYYYY` filename can enter SAAR, User Agreement, DoD Cyber Cert, 8140 Certification Memo, or training folders. Files that still fail any identity, organization, artifact, role, privileged-type, date, or extension rule are sent to the organization Rework review instead.
- Treats Active and Disabled as mutually exclusive account states and never automatically re-enables a disabled user. Official Email is the primary identity-deconfliction value after SAAR extraction; duplicate-email identities and Active/Disabled disagreements are blocked and surfaced for operator review.
- Provides a portable-launcher **Unarchive** workflow with a topmost Windows folder picker or multi-file ZIP picker, recursive discovery, 20-item paging, page/all selection, and per-file error continuation. ZIP evidence is extracted in place without overwrite while the source ZIP is retained. ZIPs reviewed for Rework are likewise extracted so correction copies remain loose PDFs without automatically deleting their source package.
- Generates daily tamper-evident audit logs with ISO 8601 UTC timestamps, a continuous sequence, and a SHA-256 hash chain. After a full verified read, append operations reuse a Windows-user-protected checkpoint only when every audit filename, length, and modification time still matches; any mismatch forces a complete chain verification. Startup, Release Health, restoration, audit viewing, and explicit verification always perform full-chain verification. Storage verification fails if an entry is changed, removed, reordered, or inserted. The Audit Log window can export a portable independent receipt containing the verified chain head and audit metadata for retention outside the mapped folder.
- Captures handled operational failures, launcher storage exceptions, uncaught browser errors, and unhandled promise rejections in one UTC-daily Notepad-readable file under `System/Error Reports`, and writes an `ERROR:` entry to the affected audit log when that chain is healthy. Errors raised before mapping are queued and flushed after a system is mapped. If the shared error-report folder is temporarily unavailable, the launcher writes the entry beneath the protected local workspace instead. The next UTC day starts a new file. Error reporting itself has a short safety limit so it cannot hide the original failure. The Performance window can export a sanitized support bundle containing fixed-schema version, session, storage-health, performance, audit-summary, and categorized-error counts only—never operator, user, or system identities; emails; filenames; paths; evidence content; or raw audit text.
- Groups tracker-owned shared support folders beneath top-level `System` (`Audit Logs`, `Error Reports`, `backup`, `Reports`, `Storage Transactions`, and `Archive Review`) and migrates compatible legacy top-level copies when a system folder is mapped. Resumable Sync journals are local per Windows user so they do not generate per-file network writes. Authoritative published evidence is stored beneath shared top-level `Organizations`; local organization-root intake, Rework, and Complete workflow areas remain under the protected per-user workspace and are never created on the share.
- Gives ordinary launcher requests and every file-changing Clean Up or Sync filename-normalization action a bounded watchdog. Resumable scans receive a larger bounded window, later queued file operations fail promptly behind a stalled storage operation, and batch actions continue to a consolidated error review when an individual file fails. Lease renewal uses a separate path and automatic background saves pause during Sync. An inactivity timeout waits for any named active storage operation, reuses an already-running final publication, then releases the lease and terminates the portable launcher only after the final verified save succeeds; a failed final save remains visibly recoverable instead of leaving an orphaned tray process.
- Generates filtered Compliance Snapshot PDF reports, stores a checksum-protected copy in each selected system's `System/Reports` folder, and records the report identifier and SHA-256 in the audit chain.
- Tracks time-limited compliance exceptions without changing the underlying Missing or Overdue status. Approvals and revocations require named approvers and justifications and are written to the audit chain.
- Retains multiple simultaneous compliance exceptions on one user. Adding or revoking one artifact exception commits against the latest User Record so a second exception cannot replace the first.
- Allows a manual privilege upgrade with a verified updated SAAR, or the existing documented SAAR override, even when newly required supporting documents are absent. The upgrade is recorded and every unsupplied requirement remains Missing; no compliance exception is required merely to apply the role change.
- Runs the Document Renamer filename gate immediately for PDF or one-PDF-ZIP files selected through drag and drop or File Explorer. The interface shows the canonical destination name, and storage fails closed when the selected user, organization, account type, artifact type, or complete date cannot produce a valid filename.
- Proposes Sync reactivation only for a newer active SAAR and requires operator approval. The comparison uses the newest disabled SAAR date or, when that filename is unavailable, the latest recorded disable-action timestamp in Administrative Change History; a re-enable entry can never be mistaken for a disable date. Manual inactivity reactivation may use the documented evidence override: when no replacement SAAR is uploaded, the newest dated disabled SAAR is moved from the permanent SAAR Archive to the active SAAR folder and canonically renamed without the `DISABLED` marker. A newly uploaded active SAAR takes precedence, supporting-evidence history is preserved, and the move or any nonblocking exception is audited.
- Splits Outlook notification recipients into safe-size, per-system BCC batches, includes the System Name in every subject, excludes active exceptions, and records a separate audit entry plus a dated User Record notification for every prepared draft batch. Network-backed notification-history, manifest, and backup writes have a bounded ten-minute window instead of the ordinary two-minute limit, and Template-folder attachment lookup uses retry-aware validation for up to five minutes so a laggy on-site or VPN share does not prematurely fail the draft. Every draft states that DoD Cyber Certifications, 8140 Certification Memos, DTA Training, Privileged User Training, and User Agreements require annual revalidation. Every draft also uses a courteous `Sir/Ma'am` salutation, anti-phishing reassurance, filename guidance, and the relevant official training link; Privileged User Training messages include the CDSE course and free-account note. User Agreement drafts attach the exact mapped-system template, while 8140 Certification Memo drafts attach the newest dated template following `8140_Qualification_Memo DDMMMYYYY.pdf` (for example, `8140_Qualification_Memo 06OCT2026.pdf`) and explain that certification details belong on the memo rather than in an attached certification. A separator before the date may be a space, underscore, or hyphen. The validated template is copied to a SHA-256-verified local temporary path before Outlook attaches it, avoiding direct attachment failures on a laggy shared drive. The temporary User Record notification clears when that record or its evidence is updated.
- Prepares a single-user Outlook draft directly from the User Record. It combines all missing, due-within-30-days, and overdue requirements, includes the applicable training links, attaches every applicable managed template, displays the number of drafts prepared during the current outstanding-paperwork cycle, and communicates the new contact-attempt number plus verified prior-draft count in the subject and message.
- Retains full-fidelity GZip-compressed JSON snapshots with matching SHA-256 files without automatic pruning. The Restore interface lists the newest 30 for usability; older snapshots remain on disk and existing uncompressed JSON snapshots remain readable for backward-compatible recovery.
- Shows Last saved, Last backup, and Last Sync health for each mapped system, with an on-demand storage verification control covering the live database checksum, newest backup, and audit chain.
- Reuses a memoized system database, CSV, and state hash while the underlying system and user records are unchanged, coalesces background edits for five seconds, and checks a protected, constant-time local status record before Session Commit touches the shared drive. A clean commit does not rebuild the CSV, renew the network lease, enumerate folders, hash evidence, or open the share. A real change reports separate local-check, evidence-preparation, shared-publication, verification, and finalization phases; database-only changes retain their evidence fast path. A successful manual Session Commit records the exact committed state hash, so closing or logging off skips a duplicate publication unless records changed afterward or recoverable evidence work remains. The Performance window reports Session Commit preparation, transfer, and finalization time, bytes transferred, throughput, whether the evidence fast path ran, publication-index shard count, and operation-scoped hash-cache use.
- Sends a lightweight browser-presence heartbeat while the app page is open, suspends both browser-session and Windows-launcher idle expiration during Sync, and restarts the idle clocks only after Sync completes, fails, or is stopped.
- Refreshes the daily backup before automatically shutting down after 60 minutes of inactivity or when the portable app's browser window closes.

This is an administrative evidence and tracking tool. It may support an organization's NIST SP 800-53 assessment activities, but it does not implement technical access controls on a tracked information system and does not independently establish compliance.

## Development

The dependency tree uses a local MIT-licensed `braces` 3.0.4 package containing the narrowly reviewed nesting-depth fix from upstream pull request 72 (commit `d0d575e55e74a4e0218e5248fafb79efc3e54ebb`) while the upstream advisory has no published patched release. The regression suite verifies both normal brace expansion and rejection of excessive nesting. Remove this backport once an official fixed version is available and the strict dependency audit remains clean. Official MIT-licensed Next.js lint packages, the MIT/Zlib `pako` PDF dependency, and `brace-expansion` 5.0.12 runtime files are also checked into `vendor/`; the latter includes the missing CommonJS package marker required by Node. The lint configuration uses the public `@babel/eslint-parser` package because the pinned Next.js package no longer ships the former internal parser path. These pinned runtime copies keep the clean-build and PDF test gates deterministic.

Requirements: Node.js 22.13 or later, pnpm 11.19.0, and Windows for the standalone executable.

The release gate includes deterministic performance-budget checks for the bounded sharded database, protected local read cache, coalesced backup path, a 10,000-record local read model, no more than 2 MB of compressed browser assets, and a no-more-than-3 MB portable executable. A release fails if those architectural safeguards are removed or a fixed CPU or package-size budget is exceeded. Full audit-chain verification remains mandatory for startup, Release Health, restoration, audit viewing, and explicit verification; it is not replaced by a weaker unsigned daily receipt.

```powershell
pnpm install --frozen-lockfile
pnpm build
.\scripts\build-portable.ps1
.\scripts\Test-ReleaseClean.ps1
```

The local browser and portable build gates run strict TypeScript and lint checks, the complete regression suite, deterministic filename/PDF/ZIP/audit and launcher-contract fuzz tests, and Windows launcher storage integration. The GitHub validation and signed-release workflows additionally run production-mode Playwright operator workflows, network-share failure injection, and metadata-enumeration qualification using 1,000-, 5,000-, and 10,000-file fixtures. A failed required check stops the build. The standalone executable and checksum are written to `release/`. Both GitHub build workflows stop before publishing if starter records, tracked runtime data, extra package files, or a checksum mismatch are detected.

Architecture boundaries, trust boundaries, and change rules are documented in [ARCHITECTURE.md](ARCHITECTURE.md) and enforced by the regression suite. GitHub default CodeQL setup analyzes both the TypeScript application and C# launcher without a conflicting advanced workflow.

## Public release setup

The signed release workflow uses Microsoft Azure Artifact Signing with GitHub's OpenID Connect authentication. Configure the `release` environment with these values:

Secrets:

- `AZURE_CLIENT_ID`
- `AZURE_TENANT_ID`
- `AZURE_SUBSCRIPTION_ID`

Variables:

- `AZURE_ARTIFACT_SIGNING_ENDPOINT`
- `AZURE_ARTIFACT_SIGNING_ACCOUNT`
- `AZURE_ARTIFACT_SIGNING_PROFILE`

After identity validation and role assignment are complete, pushing a version tag such as `v1.0.0` builds, scans, signs, verifies, checksums, and publishes the release.

Protect the `release` environment with required reviewers, restrict who can create `v*` tags, and enable private vulnerability reporting before the first public release.
